  ## Task 5: mechanism analysis
  
  **Evidence (from the original CI failure's stderr, quoted in your brief):**
  ```
  grandchild.sh: line 2: 52012 Killed: 9  sleep 4
  sh: line 1: 52011 Killed: 9  sh "grandchild.sh"
  ```
  Both lines are shell job-control termination reports, which a POSIX-family shell prints only after its own blocking `wait`/`wait4` on a *foreground* child returns showing that the child died from a signal. The ordering proves: `sleep`'s parent (`grandchild.sh`, PID 52012's parent) had its `wait4()` unblocked and returned control to its own interpreter loop, which printed the report and then executed further script text (line 3, `echo alive`) — all of this *before* `grandchild.sh` itself, in turn, received and acted on its own SIGKILL (only reported afterward, by the outer `sh`). This is direct evidence the two SIGKILLs (to `sleep` and to `grandchild.sh`) were not delivered atomically as a single event to the group.
  
  **Evidence from reading Apple's public XNU source** (fetched `bsd/kern/kern_sig.c` from `https://github.com/apple-oss-distributions/xnu`, `main` branch — this is Apple's open-source mirror; I did not confirm it is byte-identical to the exact kernel shipped in build 25G83, but its constructs, e.g. `os_reason`, `act_set_astbsd`/`thread_abort`, are consistent with modern post-Big-Sur XNU):
  - `killpg1()` (line 1675) does **not** deliver a signal to a process group as one atomic kernel operation. It calls `pgrp_iterate(pgrp, killpg1_callback, &karg, filter)` (line 1709), which walks the group's process list and invokes `killpg1_callback` (line 1642) — and that callback calls `psignal(p, signum)` (line 1664) **once per process, sequentially**, one at a time.
  - Inside `psignal_internal`'s `SIGKILL` case (around lines 2426–2458): delivering SIGKILL to a target thread does not synchronously kill it. It sets `sig_proc->p_stat = SRUN`, calls `act_set_astbsd(sig_thread)` to arm a pending BSD-AST flag on that thread, and `thread_abort(sig_thread)` to interrupt whatever it's blocked in. The actual termination happens later, when that specific thread itself runs, is scheduled, and processes the pending AST — not synchronously at the `killpg1`/`psignal` call site.
  
  Together, these two facts from the source establish the structural precondition for the race: (a) group members are signaled one-by-one in a kernel-internal loop rather than as a single atomic broadcast, and (b) even the target that's already been signaled does not die until its own thread notices the abort — a fundamentally asynchronous handoff.
  
  **Speculation (plausible given the above, but not instrumented/confirmed in this session):**
  The likely interleaving: `sleep`'s SIGKILL is processed by `killpg1`'s loop before `grandchild.sh`'s SIGKILL is (loop order is whatever `pgrp_iterate`'s internal list order happens to be — not guaranteed to be leaf-first or root-first). `sleep`'s death triggers a *separate* wakeup path for `grandchild.sh` — its blocked `wait4()` returns via the child-exit notification mechanism, which is independent of the AST-BSD signal-check path that `grandchild.sh`'s own pending SIGKILL rides on. If `grandchild.sh`'s thread resumes from `wait4()` and runs a handful of userspace instructions (print the "Killed: 9" report, evaluate the next script line, fork `echo alive`) before the kernel's next AST checkpoint fires and enforces the pending SIGKILL against that same thread, you get exactly the observed outcome. I did not trace `pgrp_iterate`'s locking discipline (whether it holds one lock for the whole loop or drops/reacquires per member) or instrument the actual thread scheduling with `dtrace`/`ktrace` to directly witness this interleaving — that remains inference from the source-code shape and the shell's own reporting, not a directly observed trace.
