  ## Findings
  
  ### BLOCKER
  - **A dropped assistant message puts `tool_result` before `tool_use`** - The `AssistantMessage` arm flushes pending user blocks before pending assistant blocks (`crates/paigasus-helikon-providers-anthropic/src/translate/request.rs:63-64`):
    ```rust
    flush_pending_user(&mut messages, &mut pending_tool_results);
    flush_pending_assistant(&mut messages, &mut pending_tool_use);
    ```
    The `System` arm (`:48-49`) and the end of the loop (`:103-104`) use the opposite, correct order. Today, an `AssistantMessage` with zero blocks is still pushed as `assistant[]`. A following `Item::ToolCall` folds into it (`:81`), and this hides the bug. The spec removes that carrier ("arms do not push a message with no blocks"). The `ToolCall` then goes to `pending_tool_use`, and the next `AssistantMessage` flushes the result first. A trace with the spec applied: `User q, Assistant[Reasoning], ToolCall tu_1, ToolResult tu_1, Assistant["done"]` becomes `user[q], user[tool_result tu_1], assistant[tool_use tu_1], assistant[done]`, which is a 400. On `main` the same items give the valid `user[q], assistant[tool_use], user[tool_result], assistant[done]`.
    A reasoning-only `AssistantMessage` followed by `ToolCall`s is a normal model-turn shape (`crates/paigasus-helikon-core/src/model.rs:517-529`, appended as-is at `agent.rs:1534`). So this is a regression for any such history: a cross-provider replay, or a session recorded with thinking on. It also happens inside one run on the third request of a tool loop.
    For blank assistant text before a tool call (for example `"\n\n"`), the fix swaps one 400 for another. The spec says the wire result is "the same as for a tool call with no assistant text". That is true, but the tool-only path (no `AssistantMessage` at all) already has this ordering bug on `main` when a `ToolResult` is followed by an `AssistantMessage`. The spec relies on that broken path. The sentence is also wrong in a second way. When `messages.last()` is an assistant message, the `ToolCall` folds into that earlier message, not into `pending_tool_use`. That earlier message can be one that `flush_pending_assistant` pushed in the same arm. | Why it matters: the fix makes sessions with the most common tool-loop shape fail, and the planned tests do not catch it. | Suggested fix: Put the ordering fix in scope, or get Sven's decision. The minimal fix swaps the two calls at `request.rs:63-64`. The exact fix also flushes `pending_tool_use` at the start of the `ToolResult` arm, and flushes pending user blocks at the start of the `ToolCall` arm before the fold check. With all three, wire order matches item order. Rewrite the bullet to match the code. Add unit tests that compare the full `messages` array with `assert_eq!`, not lengths: (a) user, reasoning-only assistant, `ToolCall`, `ToolResult`, assistant text; (b) the same with whitespace assistant text; (c) the tool-only turn with no `AssistantMessage`, which pins the bug that exists on `main`; (d) a blank assistant after a kept assistant, followed by a `ToolCall`, to pin the fold target.
