### Issues

**Important — `SessionLocks` unbounded memory growth** (`session.rs:182-212`)

The lock map `HashMap&lt;String, Arc&lt;tokio::sync::Mutex&lt;()&gt;&gt;&gt;` grows without any eviction or cleanup. `InMemorySessionProvider` is bounded by `max_sessions`, so the session map stays small; `SessionLocks` has no corresponding bound. A server that processes N distinct session ids over its lifetime accumulates N entries in the lock map indefinitely — each entry is a heap-allocated `String` + `Arc&lt;Mutex&lt;()&gt;&gt;` (~100–150 bytes), so 1 M unique ids → ~100–150 MB with no release path. The struct is `pub(crate)` and its actual consumers land in Task 10, which is the right place to wire cleanup (e.g., on session eviction from the provider). However, there is no note in the current doc comment signalling this footgun to the Task 10 implementer. The fix for this task is minimal: add a doc comment sentence to `SessionLocks` (or the `map` field) stating the known-unbounded-growth limitation and that cleanup is deferred to Task 10.
