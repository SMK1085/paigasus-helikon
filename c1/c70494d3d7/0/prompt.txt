### Important

**I1. `docs/book/src/concepts/observability-evaluation.md:294-297` — the tool-call paragraph states a conditional outcome as unconditional, and it is the wrong half of the truth.**

&gt; "Cancelling part-way through a tool call leaves a truncated `args_delta`, which core's turn accumulator then fails to parse"

That holds only when the cut lands mid-JSON. Two other cuts are reachable and land the opposite way:

- `crates/paigasus-helikon-core/src/model.rs:521-527` normalizes blank/whitespace args to `{}`. A script `[ToolCallDelta{name:Some("get_balance"), args_delta:""}, ToolCallDelta{args_delta:"{}"}, Finish]` cancelled after event 1 produces a valid `Item::ToolCall { args: {} }`.
- A script that sends complete JSON in one delta (entirely normal, and trivially what a hand-written `ScriptFile` does) cancelled after that delta also parses cleanly.

In both cases `loop_state.rs:280-281` matches on `items.iter().any(ToolCall)` **regardless of `finish_reason`**, so the loop goes to `NextAction::ExecuteTools`: **a cancelled model stream still executes the tool, then calls the model again** (popping another script, or erroring as exhausted). The book tells a reader the opposite — that a mid-tool-call cancel fails the run — which is the safe-looking case. The genuinely surprising one (a side-effecting tool runs after cancellation) is undocumented.

Failure scenario: a consumer writes a cancellation test against `MockModel` with a zero-arg or single-delta tool script, reads this paragraph, expects `RunFailed`, and instead gets a real tool invocation plus a script-exhaustion error — and concludes the mock is broken.

Also note this paragraph is an expansion beyond spec §5, which prescribed "one sentence each" for README and book. The extra prose is the only inaccurate prose on the branch. Suggested replacement:

&gt; Cancellation is a *model*-boundary event, not a run-level one: the loop treats the truncated turn as a complete turn. If the cut lands mid-JSON, `build_items` fails to parse the partial `args_delta` and the run fails with `invalid tool args for call_id=…` — matching what a real provider does when a connection drops mid-call, now reproducible deterministically. If the cut lands on a syntactically complete (or empty, hence normalized to `{}`) argument string, the tool call is well-formed and **the loop executes it**. Neither is specific to `MockModel`; both are what a real provider produces from the same cut.
