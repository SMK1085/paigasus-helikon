  #### Important (Should Fix)
  
  1. **A direct `Agent::run` consumer and `agent_as_tool` now see a cancel as a success. Nothing documents this.**
     - **Where:** `crates/paigasus-helikon-core/src/agent.rs:1520`, the early `return` with no terminal event. Also `crates/paigasus-helikon-core/src/agent_as_tool.rs:158-195`.
     - **What happens:** a cancel during a tool-call stream now ends the agent stream with no terminal event. `RunResultStreaming::collect` (`runner.rs:421`) then returns `Ok(RunResult { stop_reason: Completed, final_output: "" })`.
     - **`agent_as_tool` case:** a cancelled sub-agent gives the parent `ToolOutput("")`, which reads as a successful tool call. Under `TokioRunner`, the parent stream is dropped at its next `Pending`, so the run result is still `Cancelled`. But the recorder can already hold a `ToolReturned ""` for that call. `finalize` writes it to the session, and a later run sends it to the model as a real answer.
     - **Before this change:** the same cut stream ran the tool (worse), or failed with `Other`. So this is not a regression in safety. It is a new way for a cancel to be reported as success, and it is in the same group as the text-only cancel gap that a ruling deferred.
     - **Why it matters:** no doc says this. Core has no documented rule that every `Agent::run` stream ends with a terminal event. The book (`agent-loop.md`, "The event stream") and the core CHANGELOG do not say that a cancelled bare `agent.run` can end with no terminal event and then `collect` gives `Ok`.
     - **Fix:**
       - Add one sentence to the core CHANGELOG `[Unreleased]`.
       - Add one sentence to the "The event stream" section of the book.
       - Fix the `agent_as_tool` behavior now, or put it in the text-only-cancel follow-up. In `agent_as_tool`, when `ctx.cancel().is_cancelled()` and `result.events` has no terminal event, return a `ToolError`.
