  ## Verdict: APPROVE WITH CHANGES
  The core idea is sound. A per-block byte length with a sum check validates itself, stays in one crate, and falls back to today's bytes for old data and for most unknown shapes. Three gaps must close first: (1) the split survives the paths that drop the thinking blocks, which breaks the SMA-840 "builds as if it had no Anthropic part" contract on hand-off transcripts; (2) the cut order is ambiguous, and one reading can silently reorder text; (3) the fallback tests cannot fail against the current code.
  
  ## Findings
  
  ### BLOCKER
  None
  
  ### MAJOR
  - **The split survives the drop paths, so the SMA-840 contract breaks** - The spec splits in `assistant_blocks`. Two later passes then drop the thinking but keep the pieces as separate text blocks:
    - `drop_thinking_without_own_block` clears the slots of a lost group (`translate/request.rs:552-566`).
    - `into_output` removes the thinking from the last assistant message and clears the slots (`request.rs:527-532`).
    The documented contract says "When a rule fails, the thinking blocks are dropped, and the item builds as if it had no Anthropic part" (`request.rs:225-228`). The SMA-840 tests check exactly this with `without_anthropic` equality (`request.rs:2769-2772`, `2794`, `2817`, `2976`). With `len` data, `without_anthropic` gives one `text "AB"` block, but the new code gives `text "A"`, `text "B"`. | Why it matters: hand-off is a common path. `thread_handoff_transcript` (`paigasus-helikon-core/src/loop_state.rs:770-789`) removes the `ToolCall` items and keeps the `AssistantMessage` parts. Every multi-text response with tool calls then reaches the lost-group path. The API accepts adjacent text blocks, so nothing fails. But the invariant breaks silently, because every existing test uses `text_pos` with no `len` and takes the fallback. | Suggested fix: build one text `WireBlock` that carries its split plan (piece keys and byte ranges), with the key of the first position. Expand it in `WireMessage::into_value` after `drop_thinking_without_own_block`, and only while the block still has a slot. The last message and lost groups then keep one joined block, as today. The keep rule does not change, because a concatenation is blank only when every piece is blank. Add replay tests with `len` data for a hand-off transcript, for lost calls, and for a last assistant message. Each test asserts `messages(&items) == messages(&without_anthropic(&items))`.
  - **The cut order is ambiguous, and one reading reorders text** - The replay rules say "Collect all `Text` positions of the message in part order", and then "cut the text into one piece per position, in position order". Stream data gives the same order both ways, because blocks stop in index order and the `waiting_positions` flush keeps queue order (`stream.rs:314-317`). Hand-built or reordered parts can differ. Take positions `[(3,len 1),(1,len 1)]` in part order and the text `"AB"`. A part-order cut gives `"A"`→`At(3,1)` and `"B"`→`At(1,1)`. `sort_groups` (`request.rs:597-601`) then sends `"B"`, `"A"`. | Why it matters: the model silently gets the history text in the wrong order. No check catches this, because the sum still matches. | Suggested fix: add a splittable condition. The `Text` indexes in part order must be strictly increasing, with no duplicates. If not, fall back. Then state "cut in part order". Also fall back when a `Text` index is the same as a `Block` or `ToolUse` index of the message, because equal keys sort in no defined order.
  - **The test plan cannot prove that the fallback guards work, and it misses the risky shapes** - The three fallback tests (a length mismatch, a missing `len`, a cut that is not on a char boundary) pass on the current code without any change. They do not show that the guard, and not some other cause, stops the split. Also not covered:
    - The drop paths above.
    - The stream shapes that make the sum fall short: a text block whose stop never arrives, a `text_delta` for an index that is not open (`stream.rs:142-144` emits `TokenDelta` for any index), a block stop after the terminal event (`stream.rs:243-250`), and a repeated `content_block_start` that resets the counter.
    - Text before the first kept thinking block, end to end: `[Text A(0), Thinking(1), Text B(2), ToolUse(3)]` must replay as `[A, Th1, B, tu3]`.

    - A positive multi-byte split, for example `"é"` and `"ü"`.
    - The "more than one text part" fallback. The spec lists this case but has no test for it.
    - The multi-text shape in `session_projection_round_trip` (`translate/mod.rs:1337`).
    Also, the existing test `two_text_blocks_join_at_first_text_position` (`translate/mod.rs:1277-1313`) asserts `"AB"` and will fail. The spec says only that the "single-text tests get the `len` field". | Why it matters: the user's memory records that reviews passed code that had regressions, because the tests checked against a spec, not against the baseline. Characterization-only fallback tests repeat that pattern. | Suggested fix: pair each fallback test with a control that uses the same data with correct `len` values and does split. Add the shapes listed above. Rename and invert the `two_text_blocks_join...` test. A structured-output test needs hand-built events, because the API rejects a forced `tool_choice` with thinking on (`live_round_trip.rs:126`, `response_format.rs:67,76`).
  
  ### MINOR
  - **"A host edited the text" does not always fall back** - An edit that keeps the byte length (for example a redaction from "John" to "XXXX") passes the sum check and splits. This is harmless, because the pieces are contiguous slices, so their concatenation is always the edited text. The other side: an edit that changes the length falls back even when it is after the last thinking block, which the SMA-840 probe says the API accepts (`2026-11-21-sma-840-...-design.md:356`). | Why it matters: the spec states the behaviour incorrectly. | Suggested fix: correct the "Cases that fall back" list. Say that an equal-length edit splits and that this is harmless.
  - **A dropped blank piece changes the replayed bytes and leaves one shape unfixed** - In `[Th0, Text "\n\n"(1), Th2, Text "B"(3)]` the blank piece is dropped, so `Th2` still has a changed prefix. Today's joined replay sends the `"\n\n"`. The split replay does not. This is not a regression: I found no shape where today keeps a thinking block that the split loses. | Suggested fix: write this down as a known limit, so the decision is on record.
  - **Stored `len` values are untrusted, and the spec does not forbid a panic** - The spec checks only char boundaries. A stored `len` of `u64::MAX` overflows the sum: a debug build panics, and a release build wraps. A wrapped sum can pass the check and then slice out of range. `from_part` already treats this data as untrusted (`provider_data.rs:126-133`). | Why it matters: a panic in `build_body` fails every later request of that session. | Suggested fix: require `checked_add`, `usize::try_from`, and `str::get` with no panic, and fall back on any failure. Add a test with `len: u64::MAX`.
  - **No log on fallback** - A fallback is silent, so the debugger cannot tell why a response lost `Thinking(2)`. | Suggested fix: add a `tracing::debug!` with the reason (no `len`, sum mismatch, boundary, order) and the lengths only, never the content, as the crate already does (`provider_data.rs:110-113`). Also log a `text_delta` for an index that is not an open text block, in the style of `stream.rs:158-162`.
  - **The rollback and release facts are not stated** - The old code reads new data safely. `AnthropicData` has no `deny_unknown_fields` (`provider_data.rs:75-77`), and `text_seen` takes the first position (`request.rs:702`). But after a downgrade, a later thinking block whose signature includes the split prefix gets dropped one time under `drop_block`. SMA-840 has not shipped yet: the CHANGELOG lists it nowhere, and 0.3.1 holds only a core update (`CHANGELOG.md:8-14`). So "old data without `len`" exists only for users who build from `main`. | Suggested fix: add a short rollout note. Keep `Option<u64>`, because it costs little. Now, before the first release writes this shape into stored sessions, is the cheapest time to set the field name. Consider `bytes`, or document `len` as "UTF-8 bytes".
  - **In-code docs that the spec does not list** - These say "first text block": the module doc at `request.rs:7-12`, the comments at `request.rs:701` and `729-730`, and the `AnthropicData::Text` doc at `provider_data.rs:85`. The spec's book reference is `docs/book/src/concepts/model-providers.md`, not `model-providers.md`. Separately, the core `ModelTurn` doc (`core/src/model.rs:573-575`) says "text, reasoning and/or provider data, in that order", but `build_items` puts `Reasoning` first (`model.rs:627-633`). The spec repeats this incorrect order. The design does not depend on the order, so this is only a doc fix.
  
  ### QUESTIONS
  - Did a live probe show that today's joined replay drops `Thinking(2)`, and that the split replay keeps it? The SMA-840 table covers "inserted a text block before the thinking block", not "text joined across a thinking block". The SMA-840 non-goal (`...sma-840...-design.md:121-122`) also says "Probe finding 4 shows the API does not check order", which disagrees with this spec. The API returns `input_transformations` when it drops a block (`...sma-840...-design.md:343`), so a probe or an ignored live test can observe the result.
  - Should the last assistant message (prefill or continuation) send one joined text block, as today? The first MAJOR finding recommends yes.
  - Is there a captured trace of a multi-text response with interleaved thinking, for a fixture with a provenance header (CONTRIBUTING, "Wire-format fixtures")? Hand-built event lists are acceptable for unit tests.

  ## What's good
  - The sum check validates itself. Each source of extra `TokenDelta` bytes makes the sum fall short, so the translator falls back to today's bytes with no special code. Examples are synthesized JSON (`stream.rs:166-168`), deltas for an index that is not open, missing stops, stops after the terminal event, and backends that normalize text. Old data falls back, and old code ignores `len`.
  - I checked these invariants, and they hold. A text block is present after the split exactly when it was present before (a concatenation is blank only when every piece is blank). So `only_tool_uses`, `thinking_only`, `joins`, the tentative and rollback path (only for thinking-only items, which have no text), `is_kept_by`, and the `BeforeFirstToolUse` resolution all decide the same as today. The API does not reject adjacent text blocks, and the split never makes "the message starts with text" more likely.
  - The scope is tight. There is no core change, the rejected alternatives have good reasons, and the cut logic is a pure function that is easy to unit test.
