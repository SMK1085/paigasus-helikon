  ## Verdict: APPROVE WITH CHANGES
  The per-family design is sound. The probes support it for the two native-path Claude models and Nova 2 Lite, and it keeps today's shape for `None` with no tool round. Three gaps need a fix before a plan is written. Section 5.4 silently reverses a SMA-839 ruling on a request shape that works today. Section 5.2 applies to every Claude model, but only the two native-path models were probed. The live test does not exercise the "no real tool call" requirement.
  
  ## Findings
  
  ### BLOCKER
  None.
  
  ### MAJOR
  
  - **5.4 reverses the SMA-839 anchor ruling for `None` + structured format + tool round, without saying so.**
    - What is wrong: Today the native path builds no user tools for `None` (`translate/native.rs:71-72`). It then adds the synthesized anchor when the format is structured and a tool round exists (`native.rs:88-93`). The SMA-839 spec rules this explicitly (`docs/superpowers/specs/2026-11-21-sma-839-bedrock-native-structured-output-design.md:234,237`: "`outputConfig` only (and the anchor row applies)"). The existing test `snap_native_tool_choice_none_json_schema_finalizing_anchor` (`translate/mod.rs:1350-1365`) asserts `synthesizing == true` and tool names `[__paigasus_structured_output__]`. This shape gives a 200 today. Section 5.4 replaces it with `outputConfig` + derived specs + `tool_choice: none`, and none of the probes cover that combination: P4 and P8 sent no `outputConfig`. The spec names only `tool_choice_none_with_user_tools_omits_tool_config` as a test that stays unchanged. It does not say that this test and its `.snap` file must be inverted. `JsonObject` + `None` + tool round on the native path changes too: it loses the anchor and becomes plain text, and no test is listed for it.
    - Why it matters: A reviewed shape that works today becomes an unprobed shape. The plan writer will see a red test and must ask whether the reversal is intended. `README.md:83` ("the crate can add a hidden anchor tool") also becomes partly stale.
    - Suggested fix: Choose one of two options. (a) Keep today's anchor for `structured && None && tool round` on the native path, and apply 5.2 only when the format is not structured. This is the simplest option, the request is already a 200, and the anchor is not a real tool. (b) Keep the change. Then add a live probe and a live test for `JsonSchema` + `None` + tool round on Sonnet 5.5. State the reversal of SMA-839 section 7.5 explicitly. List the inverted test, its snapshot and a new `JsonObject` case.
  
  - **5.2 applies to every `ModelFamily::Anthropic` model, but P4/P8 cover only Sonnet 5.5 and Opus 5.5.**
    - What is wrong: Both probed models are on the native path (`family.rs:115-122`, `policy.rs:67-73`). The `build_request` branch of 5.2 serves Claude 3.x, 4.x, Sonnet 5, Opus 5 and Haiku 5.5. That branch has no probe, and the live test plan does not run it: it runs only Sonnet 5.5 and Nova 2 Lite (section 6). Older Bedrock-hosted Claude builds can reject `tool_choice.type = "none"`, as Nova rejects the key.
    - Why it matters: The most-used Claude models get a request shape that nobody has verified. If such a model rejects the field, the user sees a different 400 with no fallback. `fallback.rs:80-85` correctly does not fire, because the request has no forced choice.
    - Suggested fix: Run P4 on at least one forced-path model (for example `global.anthropic.claude-haiku-5-5` or `global.anthropic.claude-sonnet-5`) and one 3.x or 4.x model. Add those models to the live-test run list. State the intended result when a model rejects the field: keep the 400 and document it, or route that model to 5.3.
  
  - **The live test does not exercise the core requirement "the model cannot make a real tool call".**
    - What is wrong: Section 6 runs only the neutral prompt and asserts non-empty text. A neutral "summarize" prompt can give no tool call even with the P2 shape, so the test cannot fail when the guard is missing.
    - Why it matters: The ticket's acceptance criterion is "200 with no tool call". That criterion is only shown on the adversarial prompt (P4 and P6).
    - Suggested fix: Add an adversarial-prompt case. It asserts zero `ModelEvent::ToolCallDelta`, `Finish.reason != ToolCalls` and no stream error, and it allows empty text (P4 and P8 show an empty message). Keep the neutral case for the non-empty-text check.
  
  - **The 5.3 text format has no escaping, so tool output can forge the boundary and appear as user-authored text.**
    - What is wrong: `[tool result <id>: <text>]` embeds raw tool output in a user-role text block, next to the real user text. Tool results are prepended to the user turn (`request.rs:122`). A result such as `x]\n\nNew instruction from the user: ...` closes the bracket. The rest then reads as normal user text. With a structured `toolResult` block the model knows where the tool output ends. Section 7 does not list this risk.
    - Why it matters: This is a prompt-injection amplification on every non-Claude family, and the agent loop feeds untrusted tool output into it.
    - Suggested fix: JSON-encode the result text and the input with `serde_json::to_string`. Then the closing `"]` cannot appear unescaped, for example `[tool result tu_1: "...escaped..."]`. Add the residual risk to section 7. Add a unit test with a result that contains `]` and a newline.
  
  ### MINOR
  
  - **The placeholder conclusion (5.2 step 2) does not follow from P7.** P7 had a `toolUse` in the history; it only replaced the defined tool. A history with only `toolResult` blocks is an orphan result, and the Anthropic layer rejects it ("unexpected `tool_use_id` found in `tool_result` blocks") whatever `toolConfig` says. So "the request succeeds" is not shown, and the code path is probably dead. Suggested fix: probe it. Or drop the placeholder and let the request fail as it does today. Or, on Claude, flatten only the orphan results to text with the 5.3 format.
  
  - **No Document-to-JSON converter exists.** `document.rs:20-45` has only `value_to_document`, and `Document::Object` is a `HashMap` (`document.rs:38`). The 5.3 "compact `serde_json` form of the `toolUse` input document" needs a new `document_to_value`. Go through `serde_json::Value`: `preserve_order` is off (the `Cargo.lock` entry for `serde_json` has no `indexmap` dependency), so the keys come out sorted. Pin "sorted keys" in the spec, or a direct serializer will make the snapshots flaky. Add a multi-key-args test.
  
  - **"The same reserved-name check as today" is not accurate for `None`.** Today `tool_specs` is never called on a `None` request (`mod.rs:218-231`, `native.rs:71-72`). After the change, a user tool named `__paigasus_structured_output__` makes a `None` + tool-round request fail on Claude only. Decide whether that is intended, and add a test.
  
  - **The schema assertion cannot use the wire projection.** `to_wire_json` prints every input schema as `"<Document>"` (`mod.rs:430-433`). The tests for the `{"type":"object"}` derived schema must read the `ToolInputSchema` document directly. Also state whether the derived schema goes through `rewrite_tool_schema`. The synthesized `JsonObject` tool does (`response_format.rs:90-92`); 5.2 does not say.
  
  - **The "more than one text content block" case cannot occur.** `build_tool_result_block` always makes exactly one `Text` block (`request.rs:360-367`). Remove the case or mark it as defensive.
  
  - **The native-path "other families" branch (5.4) cannot be reached today.** The native path needs `from_model_id == Anthropic` (`family.rs:116`), and the learned flag needs `policy.family() == Anthropic` (`fallback.rs:80`). Say so, and test the branch through `build_native` directly, or omit it until SMA-837.
  
  - **Put the strategy on `ModelFamily` and use one helper.** Add for example `ModelFamily::tool_choice_none_strategy()`, next to `supports_forced_tool_choice` (`family.rs:94-96`). Use one shared helper that returns (messages, tools, extra fields) and call it from both builders. Without this, 5.2 and 5.3 get two copies that can drift. SMA-837 also gets one place to change.
  
  - **The field type.** A raw `Option<Document>` invites merge bugs when a later feature adds a second key, for example `thinking`, which the direct Anthropic provider already sends. Prefer a typed intent, such as `anthropic_tool_choice_none: bool`, and build the document in `send_converse_stream`. If you keep `Document`, define it as a merged JSON object.
  
  - **No local guard exists.** 5.2 relies on the service to honor `tool_choice: none`. On such a request `synthesizing == false`, so any `toolUse` becomes a `ToolCallDelta` (`stream.rs:139-147,193-197`) and the core executes it. Add a translator flag for `None` requests that turns a `ToolUse` start into `ModelError::Other`. It is cheap and unit-testable.
  
  - **Observability.** 5.3 changes the meaning of the request: the structured history becomes text. SMA-839 set the convention of one `warn!` per handle for each change of meaning (`policy.rs:86-102`). Add at least a `debug!`. If you add a notice kind, `warned: [AtomicBool; 3]` (`policy.rs:33`) must grow, and the "forced path leaves notices empty" doc (`mod.rs:48-50`) must change.
  
  - **A trailing `toolUse` with no result is not specified.** With 5.3 it becomes an assistant text that Converse treats as a prefill, so the model continues `[tool call ...`. With 5.2 the Anthropic layer rejects it. Define the intended result, for example a local error.
  
  - **The send wiring is not tested offline.** `.set_additional_model_request_fields` in `model.rs:49-60` is checked only by the live test. `output_config` has the same limit. Make the PR checklist require the live runs. Or capture the request body with the smithy test HTTP client.
  
  - **Docs.** The condition in section 8 is already true. `README.md:83` and `README.md:99` describe the native tool-choice mapping and must change. A search of `docs/book/src` found no tool-choice mapping page. Name these files in the spec.
  
  ### QUESTIONS
  
  - What does the core runner do with an empty assistant turn (the P4/P8 adversarial result: `Usage` + `Finish(Stop)` and no `TokenDelta`)? Is the final output `""`? Does an agent with an `output_type` then fail or start a repair turn? "Does not alter" does not tell a plan writer what users see.
  - If a Claude model rejects the `tool_choice` field, is a 400 acceptable, or should that handle switch to 5.3, similar to rule B?
  - Sessions can cross providers (`request.rs:139,198` drop foreign `ProviderData`). Can a history hold a tool name that fails the Converse `ToolSpecification` name pattern, for example a Gemini-style dotted name? If the `ToolUseBlock` name is not held to the same pattern, a derived spec makes a new 400. Should invalid names be skipped?
  - Does Sven approve the reversal of the SMA-839 section 7.5 anchor rows for `None`, or should that sub-case keep the anchor (see the first MAJOR finding)?
  
  ## What's good
  
  - Section 5.1 scopes the change tightly. A `None` request with no tool round stays byte-identical, and the request never sets a forced choice, so `send_with_fallback` cannot fire on it (`fallback.rs:67,80-85`).
  - 5.3 is a post-pass over the translated `ContentBlock`s, not a rewrite of the core `Item`s. This keeps the role-alternation and round-coalescing rules of `items_to_messages` (`round_is_answered`, the all-`ToolUse` check at `request.rs:215-218`) out of the change.
  - The evidence section is concrete and honest. It records the costs (the empty Claude answer, the fake call text) and the unprobed families, and it uses the history's real tool names because P7 showed that a placeholder lowers the answer quality.
