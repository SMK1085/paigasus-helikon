<result>## Verdict: NEEDS REWORK

The empirical work is genuinely good and several of the spec's factual claims check out against the code and the raw captures. But the central claim — that adding one `response.output_item.done` arm "reconciles" the two directions of the defect (§2.3) — is false as designed: the literally-reported shape in §1 stays broken unless `output_item.done` happens to arrive, so the fix swaps one unverified API invariant for another without saying so. The alternatives analysis (§3.4) also omits the option the author's own captures prove is strictly better and already parsed: `response.completed`'s `response.output` array.

## Findings

### BLOCKER

- **§3 does not establish the invariant §2.3 claims; the reported defect survives the fix** — §1 defines the bug as "a function call registered by `output_item.added` that then streams zero argument deltas ends the stream with `Finish{ToolCalls}` and no `ToolCallDelta`". §3's arm only repairs that when `output_item.done` *also* arrives. With `added` → `completed` (no deltas, no `done`), `item_to_call` is still non-empty at `backend/responses.rs:401`, so `terminal_events` at `:503` still returns `ToolCalls` with zero `ToolCallDelta` emitted. Symmetrically, the buffered-deltas-with-no-`added`-and-no-`done` case still drops data silently (`pending_args` at `:388-391` is never drained anywhere except the `added` arm at `:342`). §2.4 argues the fix's value is that "it removes the translator's dependence on an undocumented API behaviour ('a function call always streams at least one argument delta')" — but §3 substitutes an equally undocumented one ("a function call always emits an `output_item.done`"), and the spec never acknowledges the substitution. Test 2 in §4 is *synthetic* and is constructed to include the `done` event, so the suite will not reveal the residual gap. | Why it matters: an implementer ships this, closes SMA-562, and writes a CHANGELOG entry claiming a fix for a shape that is still broken; the "silently drops a real call" half is also only partially repaired. | Suggested fix: state the residual gap explicitly, **or** move the reconciliation to the terminal event. `async_openai::types::responses::Response::output: Vec&lt;OutputItem&gt;` is a non-`Option` field (registry `async-openai-0.41.3/src/types/responses/response.rs:2876`) that is already deserialized on every `ResponseCompleted`/`ResponseIncomplete` event, and every one of the four captures carries the complete function-call items in it (`.capture/zeroarg-raw.txt:20`, `.capture/bg-raw.txt:35`, `.capture/resume-raw.txt:5`). Reconciling `e.response.output` against `name_emitted` inside the `ResponseCompleted` arm at `backend/responses.rs:397-402` — emitting a `ToolCallDelta` for every `FunctionCall` item not yet emitted, then delegating to `terminal_events` — costs no new state, uses the same dedup key, covers §1 **and** §2.2 **and** the added-without-`done` case, and preserves the SMA-522 invariant (`Finish` still appended last at `:513`). §3.4 must at minimum address and reject it on the record.

### MAJOR

- **§2.4's "one request flag away" is contradicted by the author's own capture** — the spec says §2.2's stream "is reachable on the wire, one request flag away — `CreateResponse` already carries `background: Option&lt;bool&gt;`". `.capture/bg-raw.txt` is a `background: true` request and it streams `output_item.added` (line 11) plus five argument deltas (lines 14-26) exactly like a foreground call. §2.2's delta-free stream came only from a *second*, separate `GET /v1/responses/{id}?stream=true&amp;starting_after=9`. I confirmed the crate has no retrieve/resume path at all (`grep background|starting_after|retrieve` over `crates/paigasus-helikon-providers-openai/src` returns nothing but `previous_response_id`). | Why it matters: §2.4 is presented as the "honest statement of reachability" and is the sole rebuttal to §3.4's "close as not-reproducible" option; overstating it by an order of magnitude undermines the one section whose job is candour. | Suggested fix: restate as "requires `background`/`store` **plus** a retrieve-and-resume entry point that does not exist and is explicitly out of scope — the flag alone is not sufficient, as `bg-raw.txt` shows."

- **Test 1's level is self-contradictory and the fixture cannot be driven through the public API** — §4 says "All four live in the `#[cfg(test)] mod tests` of `backend/responses.rs` unless noted", and notes only test 4 as an integration test; but §4.1 says `responses_tool_call_resumed.txt` "Drives test 1". The unit module constructs typed `ResponseStreamEvent` values directly (`backend/responses.rs:526-550`) and does no SSE parsing, so it cannot consume a `.txt` fixture. The integration helper is `run()` at `tests/responses_streaming.rs:29-50`, which mocks only `POST /responses` — the resumed stream is a `GET .../{id}?stream=true&amp;starting_after=9`, so serving it from the POST mock is a fiction the fixture header would have to disclose. | Why it matters: two engineers build different things; and if test 1 lands as a unit test the fixture becomes an unreferenced file (or, if `include_str!`'d and unused, a `dead_code` warning that fails the required `clippy --workspace --all-features --all-targets -- -D warnings` gate). | Suggested fix: pick one. State explicitly that the resumed fixture is served over the POST mock as a translator-level harness and say so in its provenance header, or drop the fixture and keep test 1 as a pure typed-event unit test.

- **Test 4 cannot do what §4 claims it does** — "This is what turns §2.4's 'undocumented API behaviour' into something the suite notices if it changes." A wiremock fixture is a frozen recording; if OpenAI stops emitting the `"{}"` delta tomorrow the fixture is unchanged and the test still passes. Nothing in the offline suite can observe an upstream behaviour change. | Why it matters: the spec sells a guarantee the design cannot deliver, and reviewers will accept it. | Suggested fix: either drop the claim and describe test 4 as a plain regression pin, or add the assertion where it can actually fire — `crates/paigasus-helikon-providers-openai/tests/live.rs` already has an env-gated `#[ignore]` suite (`responses_smoke` at `:47-61`, `chat_tool_call_round_trip` at `:63`) that is the correct home for "the API still streams ≥ 1 delta for a zero-arg tool".

- **`response.incomplete` interaction is unexamined and the arm can turn a working turn into a hard error** — §3 emits `item.arguments` verbatim and never inspects `FunctionToolCall.status` (`Option&lt;OutputStatus&gt;`; variants `InProgress`/`Completed`/`Incomplete`, registry `response.rs:222-226`, `:2228-2231`). A turn truncated by `max_output_tokens` can emit an `output_item.done` carrying a partial, invalid JSON `arguments` with `status: "incomplete"`. Today no deltas → no `ToolCallDelta` → the consumer gets `Finish{Length}` and `ModelTurnAccumulator::finish` succeeds. After the change it emits a `ToolCallDelta` with unparseable args and `build_items` returns `Err("invalid tool args for call_id=…")` (`crates/paigasus-helikon-core/src/model.rs:530-535`), failing the entire turn. | Why it matters: a strictly-worse unhappy path introduced by a fix that claims to be bounded and safe. | Suggested fix: state the decision explicitly — either skip emission when `fc.status == Some(OutputStatus::Incomplete)`, or document why a truncated tool call should surface as a turn-level parse failure. Add a test.

- **Parallel tool calls are never mentioned, captured, or tested** — the ticket is about tool calls, `parallel_tool_calls: true` is on in every capture (`.capture/zeroarg-raw.txt:2`, `.capture/bg-raw.txt:2`), and the Chat backend already carries a `chat_parallel_tool_calls.txt` fixture — but there is no Responses parallel capture and §3/§4 say nothing about interleaved items sharing one stream. ### MINOR

- **Discarding `pending_args` on `done` can lose data when `done.arguments` is empty** — §3 step 2 discards unconditionally and emits `item.arguments`. The `added` arm guards its flush on `!buffered.is_empty()` (`backend/responses.rs:343`); §3's arm has no symmetric guard on `item.arguments`. `output_item.added` demonstrably carries `arguments: ""` on the wire (`.capture/zeroarg-raw.txt:8`), so an empty-`arguments` `done` is not unthinkable. | Suggested fix: `if item.arguments.is_empty() &amp;&amp; !buffered.is_empty() { emit buffered } else { emit item.arguments }`.

- **The design assumes `output_item.done` is terminal for its item, but never says so** — if any delta for `item_id` arrives *after* its `done`, the delta arm at `:364-377` finds `name_emitted` set and `item_to_call` populated, and emits `ToolCallDelta { name: None, args_delta }`, appending to an already-complete args string and producing malformed JSON. Not observed on the wire (`starting_after` truncates a prefix, so order is preserved), but the translator otherwise goes out of its way to tolerate reordering. | Suggested fix: state the assumption in §3 and in the arm's comment.

- **`output_index` is never mentioned** — it is present on `ResponseOutputItemDoneEvent` (registry `stream.rs:196-200`) and ignored by the design. That is correct (`item.id` is the unique per-item correlator and `output_index` adds nothing), but a reader cannot tell whether it was considered or overlooked. One sentence in §3 fixes it.

- **§3.3's "core's existing normalization covers it" is true only for `ModelTurnAccumulator` consumers** — `build_items` does normalize blank args to `{}` (`crates/paigasus-helikon-core/src/model.rs:525-529`), verified. But the AG-UI mapper forwards `args_delta` verbatim into `TOOL_CALL_ARGS` frames with no normalization (`crates/paigasus-helikon-runtime-agentcore/src/agui/map.rs:158-190`), so an `args_delta: ""` reaches an AG-UI client as an empty-args span, not `{}`. | Suggested fix: narrow the claim, or have the arm emit `"{}"` when `item.arguments` is empty.

- **Orphaned `pending_args` are still dropped silently at end of stream** — same "the stream lies" family as §2.3, unaddressed. A `tracing::warn!` in the terminal arms when `pending_args` is non-empty would make it observable for the same cost as the existing debug log at `:383-387`.

- **The `output_item.done` debug log is lost** — the new arm removes the event from the trailing `other` arm at `:441-448`, so nothing is logged when a non-`FunctionCall` `done` or an `id: None` `done` is dropped. Keep a `tracing::debug!` on those fall-through paths.

- **`.capture/` is not gitignored** — `.gitignore` (lines 1-13) covers `/target`, `.env`, and some `.claude/` paths only. The spec never says whether the raw captures are committed, discarded, or moved. They contain multi-kilobyte `encrypted_content` reasoning blobs (`.capture/zeroarg-gpt5-raw.txt:8`). Given this repo's standing "never `git add -A`" hazard, state the disposition.

- **The SMA-522 `Usage`/`Finish` ordering invariant is unmentioned** — the arm complies (it emits only `ToolCallDelta`), but the invariant note at `:473-477` explicitly warns that "a future arm emitting `Usage` elsewhere would break it". A one-line "this arm emits no `Usage`" in §3 is cheap insurance.

### QUESTIONS

- With the fix in place, what exactly is the post-condition? Is it "`Finish{ToolCalls}` ⟹ ≥ 1 `ToolCallDelta`"? If so, the BLOCKER shows it does not hold. If the intended post-condition is weaker, state it precisely — that is the thing the tests should assert.
- Was `response.function_call_arguments.done` considered as the reconciliation point? It carries `item_id` + complete `arguments` (`.capture/bg-raw.txt:29`) but no `call_id`/`name`, so `output_item.done` is the better choice — but §3.4 should say the comparison was made rather than leaving a reader to rediscover it.
- `Tool::Function` is the only tool the crate builds (`backend/responses.rs:111-125`), but `OutputItem` also has `CustomToolCall`, `McpCall`, `LocalShellCall`, `ShellCall`, `ApplyPatchCall` variants (registry `response.rs:3021-3066`). Given `paigasus-helikon-mcp` exists in the workspace, is a non-`FunctionCall` tool item ever reachable here, and if so does it produce the same `has_tool_calls`/no-delta mismatch?
- §4 test 3 (`done_after_deltas_does_not_double_emit`) is largely already covered end-to-end: `responses_tool_call.txt:98-99` already contains an `output_item.done` after five deltas, and `tool_call_turn_finishes_with_tool_calls` (`tests/responses_streaming.rs:148-210`) already asserts the reassembled args equal `{"city":"Berlin"}` and exactly one named delta. Is the new unit test adding coverage, or restating it?
- What is the rollback story? The spec has no §7. If this arm turns out to double-emit against a wire shape not captured here, is the answer a revert, or is there a reason none is needed?
