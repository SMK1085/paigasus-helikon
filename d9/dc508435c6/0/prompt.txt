### MAJOR

- **Ring-capacity bump mis-analyzes memory: single-run framing ignores the `max_runs` multiplier** — `src/event_log.rs:80`, `EventLog::new`. The spec justifies `min(64) → min(1024)` as "tens-to-low-hundreds of KB" for *one* run. But `EventLog::new` is called per run at `registry.rs:87`, and the registry retains up to `max_runs` completed runs (default **1024**, `server.rs:104`) for the full `retention` window (default **300s**, `server.rs:103`). Every run — including a 2-event one-shot echo — now preallocates a 1024-slot `VecDeque&lt;AgentEvent&gt;` and holds it until TTL eviction. `sizeof(AgentEvent)` is large (its biggest variants embed `Item`/`serde_json::Value`); even at a conservative ~50-90 bytes, steady-state worst case is ~50-90 MB of mostly-empty ring capacity vs ~3-6 MB under the old `min(64)` — a ~16x regression. Worse, the *benefit* is nil for the common short-run case (a 2-event run did zero reallocs at cap 64 already); it only helps runs emitting 65-1024 events (saving ~4 cheap amortized-O(1) doublings). | Why it matters: a "perf" change introduces a real, unbounded-by-design memory regression to a server runtime, for marginal gain on an uncommon run size. | Suggested fix: the actual O(n)-replay win comes entirely from the `subscribe` rewrite; keep that and either drop the capacity bump, keep `min(64)`, or use a smaller initial cap (e.g. `min(128)`) and let the cheap amortized growth handle the long tail. At minimum, re-do the memory math across `max_runs` and state the steady-state footprint.

- **"Make it required" is under-specified and rollout-hazardous** — Task 2, `main-protection-checks.json` + CONTRIBUTING/CLAUDE.md. Editing `.github/rulesets/main-protection-checks.json` is *inert* on its own: CONTRIBUTING.md:287 states "There is no drift-check CI job" — the ruleset only takes effect when a maintainer runs `scripts/apply-repo-config.sh`. Separately, applying the new required context is order-sensitive: GitHub will block *every* open PR that lacks a report for the new context, including the release-plz `chore: release` PR that publishes this very crate's bump and any in-flight Dependabot PRs whose branches predate the job — exactly the "dropped context blocks merge" failure mode. | Why it matters: either the gate does nothing, or it deadlocks the crate's own release PR. | Suggested fix: spell out the sequence — (1) merge the `ci.yml` job and confirm it reports on `main` and on PRs, (2) then edit the ruleset JSON, (3) run `scripts/apply-repo-config.sh`, (4) rebase/re-run any open PRs (notably the release-plz PR) so the new context reports.

- **Test coverage omits the most regression-prone branch of the broadened invariant** — Task 1 tests. The spec broadens the invariant to cover panic-mid-stream and "real events then no terminal," but every proposed test uses `FailingRunner` (zero events, `start_error = Some`). - **No observability on synthetic-frame emission; panic reason is swallowed** — Task 1. When a streaming transport synthesizes `RunFailed { error: "run ended before producing a terminal event" }` (the panic-mid-stream / terminal-less-stream case), nothing is logged server-side and the actual panic/cause is lost (the writer's `JoinHandle` is never awaited at `runs.rs:277`). A `tracing::warn!` at the synthesize point would make these otherwise-invisible failures diagnosable. Not required, but cheap and worthwhile.

- **SSE mechanics under-specify the state** — Task 1 / `sse_response` (`runs.rs:330`). To call `handle.synthetic_terminal_frame(...)` in the stream-end branch, the unfold must also carry/capture an `Arc&lt;RunHandle&gt;` (or a clone of `start_error`); the spec lists only `saw_terminal` and `done` "alongside the event stream and the cancel DropGuard." Trivial, but call it out so the implementer doesn't try to reach a `handle` that isn't in scope.

- **WS test setup is imprecise** — Task 1 WS test note (spec §"Tests (Task 1)" and the boxed note). A start-error WS test needs a server with *both* `FailingRunner` *and* a registered agent named in the URL (`create_run` resolves the agent at `runs.rs:154` before spawning the writer, so an unregistered name 404s before any run is created). The existing `start_error_returns_500_not_hang` shows the pattern (ScriptedAgent "echo" + FailingRunner); the spec's "a server built with FailingRunner" omits the agent.

- **Book page doesn't document the streaming error model at all** — `docs/book/src/concepts/axum-server.md:84-86` describes one-shot/SSE/async but says nothing about start-error/terminal-less close behavior. The spec's conditional ("if it documents 'streams close cleanly'…") will find nothing to edit; the correct action is to *add* the new "streams emit a final `run_failed` frame, then close" behavior, not just patch an existing line.

It checks out against all five existing `event_log` tests.
