  - **The guard "no `Text` part" changes behavior for providers other than Gemini.**
    - What is wrong: OpenAI Responses, Anthropic, Bedrock and LiteLLM already produce `AssistantMessage[Reasoning]` with no `Text` part (a reasoning plus tool-call turn). With the spec's guard, these effects change:
      - `runner.rs:434-443` (`collect`) no longer clears `final_output`. A run that defers or stops after such a turn now returns old intermediate text, where today it returns `""`.
      - `workflow.rs:32-46` `assistant_text` returns `None` where today it returns `Some("")`. This changes `state[key]` in the Sequential, Parallel and Loop agents and in `graph.rs`.
      - The CLI newline (`cli/src/repl.rs:221`) and the AG-UI thinking-span close (`agui/map.rs:366-392`) also change.
    - Why it matters: The spec's own anti-goal says the text that users see must not change. These changes are silent and come from the predicate, not from provider data.
    - Suggested fix: Use the predicate "the message holds only `ProviderData` parts". Such messages did not exist before, so this keeps today's behavior exactly. Put it in one public core helper, for example `Item::is_provider_data_only()`, so that core, CLI, agentcore, axum and actix share one rule. Test it with a differential test: send the same scripted event stream with and without provider-data events through `collect`, `collect_typed`, the workflow agents, `EventMapper`, `RunResponse::from_events` and the REPL, and assert identical output.
  
  - **There is no rollout or rollback plan for a persisted serde variant.**
    - What is wrong: `provider_data` parts are written automatically, with no opt-in, to these places:
      - Session stores (the sqlite, postgres and redis JSON payloads).
      - Temporal history: `ModelTurnResult`, `WorkflowInput.conversation`, the `ModelRequest` input of every model activity, and `DurableRunOutcome.events` (`runtime-temporal/src/payloads.rs:22-83`).
      - HTTP responses: `RunResponse.events` and SSE (`runtime-axum/src/handlers/events.rs:111`).
  
      A reader on the earlier core version fails with "unknown variant `provider_data`". The codebase already documents this hazard for `ToolDeferred` (`core/src/session.rs:152-154`), but that variant is opt-in. Here, every Gemini 3 turn writes the new variant. If capture 2 finds a text signature, this includes text-only turns, which work today.
    - Why it matters: During a rolling deploy, old pods cannot read sessions that new pods wrote. A Temporal workflow worker older than its activity workers cannot decode activity results. A rollback leaves sessions and workflows that cannot be read.
    - Suggested fix:
      - Add a "Rollback note" to the rustdoc of both variants, the CHANGELOG and the book.
      - State the deploy order: readers and workflow workers first.
      - Consider not storing text-level signatures in this PR. Google documents them as optional, and the spec already drops one when no text part exists. Then only tool turns, which fail today anyway, change format.
      - Optionally, add a `GeminiModel` builder opt-out.
  
  - **The live acceptance test cannot fail when the real-signature path is broken.**
    - What is wrong: The fallback puts the dummy on any content with no real signature, and SMA-820 proved that the dummy gets HTTP 200. Suppose the stream translator drops signatures, or the `call_id` scoping never matches. Both live tests still "end with `Finish` and no error".
    - Why it matters: Goals 2 and 3 then have no end-to-end proof. The scoping logic is the most complex part of the change, and its failure is silent.
    - Suggested fix: In each live test, assert two things:
      - Turn 1 gives at least one `ProviderData { provider: "gemini", call_id: Some(_) }` with a non-empty signature.
      - The turn-2 request body holds that exact signature and not the dummy.
  
      The second assert needs the `pub(crate)` translator. So put the test in `src/` as `#[cfg(test)] #[ignore]` and call `build_request`, or use a transport that records the request.
  
  - **The parallel-order rule is on the common path and can be incomplete.**
    - What is wrong: The spec ignores the in-repo live capture at `tests/provider-stream-conformance/tests/conformance.rs:2225-2274` (gemini-3.6-flash, 2026-08-20). It shows three facts:
      - `functionCall.id` is present (`"call_1285087"`).
      - `thoughtSignature` is a sibling of `functionCall`, about 700 characters long.
      - The STOP chunk carries `{"text":""}` with no signature.
  
      So native ids are the normal case, and the synthesized `fc_N` ids are the fallback. `BTreeMap` order (`model.rs:514,530`) of random native ids puts the signed call second in about half of the two-call turns. The rule "signed first, keep the order otherwise" restores only position 0. With three or more calls, the unsigned calls stay in sorted order, not in emitted order. If Gemini checks more than "the first part is signed", those turns fail. The dummy cannot help, because the content already has a real signature. The `fc_10` vs `fc_2` test is a case that the stream cannot produce, because a synthesized `fc_0` always sorts first.
    - Why it matters: Parallel calls are common. A failure here is a hard HTTP 400 with no fallback.
    - Suggested fix:
      - Emit one `ProviderData` per `functionCall` part with its emission index: `{"index": i}`, plus `thoughtSignature` when present. The request translator then restores the emitted order exactly.
      - Extend capture 4 to three calls: (a) the signed call is not first; (b) the signed call is first and the two unsigned calls are swapped.
      - Cite the existing capture, and reduce capture 1 to a re-check on 3.8.
  
  - **The live and probe coverage skips the shapes that carry the risk.**
    - What is wrong: These shapes are not covered:
      - Two sequential tool rounds in one current turn: user text, model fc (sig A), fr, model fc (sig B), fr, model. Gemini validates both steps, and with synthesized ids both use `fc_0`. This is the exact repeated-id case that the scoping rule exists for. The spec's "two-turn tool loop" with "no trailing user text" covers one round only.
      - The structured-output finalizing request on Gemini 3. It has `tools: []` (`loop_state.rs:383-387`), signed calls in the current turn, and the unconstrained answer as a trailing `model` content (`agent.rs:1518` runs before `transition`). This path could not run on Gemini 3 before, because the loop failed at call 2.
    - Why it matters: These are the first production uses of these request shapes.
    - Suggested fix: Add a probe capture and an `#[ignore]` live test for each shape: a two-round `LlmAgent` loop, and `LlmAgent` with `output_type` plus one tool.
  
  - **Signature validity is not bound to a model or an endpoint.**
    - What is wrong: The key `"gemini"` covers both the Developer API and Vertex, and every Gemini model. `data` holds no model id. A real signature that goes to a different model is treated as real, so no dummy is used. This happens after a model change between deferral and resume, a fallback chain, an A/B test, or a handoff to a Gemini agent on another model. The live check covers one model on the Developer API only. The SMA-820 spec also says "Vertex uses the same translator", not "Vertex was tested".
    - Why it matters: If Gemini rejects a foreign signature, the request fails with no recovery. The SDK has no data to detect the mismatch. Stored sessions written without a model id cannot be repaired later.
    - Suggested fix: Store `{"thoughtSignature": s, "model": <model_id>}`, and maybe the transport too. The translator uses the dummy when the model does not match. Add probe captures: a 3.8-flash signature sent to another Gemini 3 model, and one Vertex run. If they are not done, document the limit.
  
  ### MINOR
  - **The dummy is applied to every model content, not only the current turn.** Gemini validates only the current turn (SMA-820 probe shapes 2 and 4). Google says the dummy can lower answer quality. The rule also changes about 10 exact-JSON tests in `translate/request.rs` and 2 snapshots (`snap_tool_call_and_result`, `snap_parallel_same_name_tool_calls`), and the spec does not list them. Suggested fix: apply the dummy only to model contents after the last `user` content with no `functionResponse` (shape 3 shows that a `Mixed` content does not start a new turn). Or keep the current rule, state why, and list the test and snapshot churn.
  - **The pending-signature lifetime is fragile.**
    - "The last `AssistantMessage`" replaces the earlier list. In a `ParallelAgent` log that interleaves siblings, one sibling's signatures are lost, or they go to the other sibling's `fc_0`.
    - Clearing at the next `ToolResult` drops a later call's signature when `close_open_transfers` inserts a result between two calls of one response (`resume_exec.rs:185,194`).
    - A `ToolUse` part that comes before the `ProviderData` part in the same message is missed, unless the translator scans the message's provider data first. The rustdoc phrase "after this AssistantMessage" also excludes same-message `ToolUse` parts.
  
    Suggested fix: scan each message's provider data first. Clear the list only at the next `AssistantMessage` or the next non-result `UserMessage`. Write down the trade-off for damaged histories.
  - **Foreign or misplaced parts make warnings on every request.** Bedrock warns for each unknown part (`providers-bedrock/src/translate/request.rs:138-143, 195-200`). The Gemini `user_parts` path warns too (`request.rs:246-251`). The rule "ignored without a warning" in the spec covers only Gemini `assistant_parts`. Suggested fix: add an explicit silent arm in each translator, and list Bedrock as a touched crate.
  - **Provider data outside an `AssistantMessage` is not handled.**
    - HTTP clients can send any `Item` (`runtime-axum/src/dto.rs:42-47`). In OpenAI Chat and LiteLLM, a `UserMessage` that holds only provider data goes through `user_message` and gives `{"role":"user","content":[]}`, which is an invalid request (`providers-openai/src/translate/request.rs:106-159`).
    - The behavior for a malformed own part (a non-string or absent `thoughtSignature`) is not specified.
  
    Suggested fix: the rustdoc says the part is valid only in an `AssistantMessage`. Each translator ignores it elsewhere. Gemini treats a malformed signature as unsigned and never returns an error. Add tests for both cases.
  - **Provider names are ambiguous.**
    - "`ProviderData` is a public constant-like name per provider" is garbled.
    - It says "public", but the code is `pub(crate) const`.
    - OpenAI Chat and OpenAI Responses both report `provider() == "openai"` (`providers-openai/src/model.rs:70-72`). Under "read parts whose provider equals its own name", Chat would later read the Responses `encrypted_content`.
  
    Suggested fix: define the key as a wire-format id that one translator owns, which is not `Model::provider()`. Export the constants publicly so that hosts can filter or strip the data.
  - **The AG-UI instruction asks for a change that is not needed.** Today a text-plus-tool `MessageOutput` already closes the open call span (`map.rs:370`) before `ToolCallItem`, so the frames are identical either way. Separately, suppressing an empty `TokenDelta` changes AG-UI frames: `map.rs:236-243` opens a text span on an empty delta. Decide that on behavior, not with "keep it if a test depends on it". Use the differential test from the guard finding.
  - **Goal 5 is partly false and has no tests.** `thread_handoff_transcript` (`loop_state.rs:770-789`) drops every `ToolCall` and `ToolResult`. After a handoff, call-scoped signatures are orphans, and the target can be another provider. Suggested fix: reword the goal. Add tests for three things:
    - `SessionRecorder` records `AssistantMessage[PD]` before `ToolCalled`.
    - `project()` of that log, sent through the Gemini translator, attaches the signature.
    - A `ModelTurnResult` with provider data survives a serde round trip.
  - **Docs are definite, not "if one exists".**
    - Book pages: `docs/book/src/concepts/core-primitives.md:35`, `model-providers.md:55` and the Gemini Limitations section (296-300), `sessions.md:270-274` (the token-count rules need "provider data counts 0"), and `agent-loop.md:64-69` (`MessageOutput` now also comes on tool-only turns).
    - The Gemini README has a Limitations section (`README.md:89`).
    - The CHANGELOG must name this behavior change: user code that renders each `MessageOutput` now gets messages with no text on every Gemini 3 tool turn.
  - **The token-count decision can use evidence.** The probe can compare `usageMetadata.promptTokenCount` for the same history with the real signature and with the dummy, and record the signature length. The in-repo capture shows about 700 characters. Every Temporal model activity input repeats the whole conversation, so the signature bytes are copied on every turn.
  - **The test wording is ambiguous.** "A run that ends after a tool-only turn" must name its stop path: `RunDeferred` from a deferred tool, or `RunStopped` from a `TurnCheckpoint`.
  - **Error and log size grows.** Both enums derive `Debug`. `loop_state.rs:646-651` formats the whole `TransitionInput` into a `RunFailed` error string, so signatures appear in errors and logs.
  - **Add a conformance rule.** In `tests/provider-stream-conformance/src/check.rs`, add the rule "a `ProviderData` with `call_id: Some(id)` references a `ToolCallDelta` id in the same stream". This is a cross-provider guard for the Anthropic follow-up.
  - **Do not commit real signatures.** Keep real signature values out of the public PR body and the fixtures. The in-repo convention elides them (`conformance.rs:2228, 2270-2274`), and the translator treats them as opaque, so a placeholder is enough.
