## Verdict: NEEDS REWORK
The core architecture is sound and salvageable — the append-only EventLog/replay model, routing every run through the `Runner` trait (not bypassing it like `mcp` does), the test plan, and the release ritual are all correct against the real code. But three things must be fixed before this is safe to implement: the §6 error/status model is **unimplementable** against the chosen "single writer drains `run_streamed`" mechanism (and risks a permanent hang), the per-request `RunContext` construction — the heart of execution — is under-specified (cancel token, hooks, tracer, and the entire permission/guard posture), and one route-syntax error will panic on axum 0.8. None require a teardown, but §6 and §5's RunContext wiring need real rework, not tweaks.

## Findings

### BLOCKER

- **Route param syntax is axum-0.7, workspace is on axum 0.8** — The spec uses `:name`/`:id` throughout (§2 diagram, §5 routes table, e.g. `/agents/:name/runs/:id/events`). The workspace pins `axum = { version = "0.8", ... }` (`Cargo.toml:20`). axum 0.8 replaced `:param` with `{param}`; `:name` is rejected at `Router` construction with a panic. | Why it matters: every route panics the moment `router()` is built — AC1 (curl) can never pass. | Suggested fix: respec all paths as `/agents/{name}/runs`, `/agents/{name}/runs/{id}/events`, etc.

- **§6 status model can't be produced from the drained EventLog, and a start-failure can hang the request** — §2/§3 route *all* modes through one writer task draining `Runner::run_streamed`. But `run_streamed` (`runtime-tokio/src/lib.rs:194-258`) surfaces timeout/cancel as *synthetic in-stream* `AgentEvent::RunFailed { error: "run timed out" }` events and returns `Ok`; it returns the outer `Err(RunError)` **only** for session-load failure or agent-start failure (`:200-209`). The `RunError::Timeout`/`Cancelled` variants are only reachable through the non-streaming `Runner::run` (`:187-191`), which the design never calls. So: (a) §6's "timeout → 504, RunError → 500" mapping is unreachable — the plain-POST handler reads an EventLog containing only a `RunFailed` *string* and cannot distinguish timeout from agent failure without string-sniffing "run timed out"; and (b) the `EventLog` struct (`events: Vec&lt;AgentEvent&gt;, terminal: bool`, §3) has **no slot for an outer `RunError`**, so when `run_streamed` returns `Err` (e.g. session backend down) the log never gets a terminal event and a plain-POST awaiter blocks forever. | Why it matters: a plausible input (session store unavailable) hangs the request; the documented HTTP status contract is not implementable. | Suggested fix: add an explicit error/terminal channel to `RunHandle` (e.g. `Mutex&lt;Option&lt;RunError&gt;&gt;` set by the writer's `Err` arm), define how the writer folds an outer `RunError` into a synthetic terminal, and decide plainly whether plain POST is *always* 200-with-terminal-in-body (consistent with "RunFailed is data") or genuinely differentiates 500/504 — the latter requires plain POST to use `Runner::run`, a second code path the §3 unification was meant to avoid.

### MAJOR

- **Per-request `RunContext` construction is under-specified — including the security posture** — Providers yield only `Arc&lt;Ctx&gt;` (`ContextProvider`) and `Arc&lt;dyn Session&gt;` (`SessionProvider`), but `RunContext::new` requires five args: `user_ctx, session, hooks, tracer, cancel` (`context.rs:106-112`). The spec never says where `hooks`, `tracer`, and `cancel` come from, and there is **no** way to configure `permission_mode`, `deny_rules`, `guard_rules`, `approval_handler`, or `redact_output` (all `RunContext` setters, `context.rs:350-439`) — `RunConfig` (the only knob, §5 `.run_config()`) carries none of these. For a network-exposed, tool-calling agent this silently pins core's defaults (no approval handler ⇒ `AskUser` denies; default guards on) with no operator override. | Why it matters: leaky abstraction (providers expose two of seven inputs) plus an unaddressed security surface in a codebase that invests heavily in the permission layer. | Suggested fix: either have `ContextProvider` return a fully-built `RunContext&lt;Ctx&gt;` (then the server only injects the run's cancel token), or add explicit builder knobs for hooks/tracer/permissions; and state exactly how the run's `CancellationToken` (the `RunHandle.cancel`, §4) is threaded into `RunContext::new` — without that, cancel-on-disconnect is unwired.

- **`DefaultContextProvider` "blanket → zero-wiring for `()` + runtime error for non-`Default`" is not expressible as described** — §5 says a blanket gives `Ctx = ()` zero wiring while a non-`Default` `Ctx` "must supply a `context_provider`, else `build()` errors." But `build()` is generic over `Ctx: Send + Sync + 'static` (`AgentServerBuilder`, §5), so it cannot synthesize `DefaultContextProvider::&lt;Ctx&gt;::default()` (that needs `Ctx: Default`, unavailable without specialization). There is no single generic `build()` that succeeds for `()` yet returns a runtime `Err` for non-`Default`. The default can only be installed at a `Ctx: Default`-bounded site — exactly what `mcp` does with `with_default_ctx` (`mcp/src/server.rs:65-70`, a `where Ctx: Default` constructor, with `handler()` erroring at runtime if unset). | Why it matters: two engineers will build divergent APIs from this sentence; the literal "blanket" reading does not compile. | Suggested fix: pick one — a compile-time `Ctx: Default`-bounded zero-config entry point (`builder()`/`build()` for `Default`, `context_provider()` for the rest; non-`Default` users get a compile error, which is strictly better than the spec's runtime error), or mirror `mcp`'s `with_default_ctx` opt-in. Then drop "blanket."

- **Default `InMemorySessionProvider` has no eviction → unbounded growth from client-supplied `X-Session-Id`** — §5 keys sessions in a `RwLock&lt;HashMap&lt;String, Arc&lt;dyn Session&gt;&gt;&gt;`. Runs get TTL+LRU (§4) but the session map gets neither. A client (or attacker) sending N requests with N distinct `X-Session-Id` values retains N `MemorySession`s forever. | Why it matters: trivial memory-exhaustion DoS on a network service. | Suggested fix: bound the session map (TTL/LRU like runs) or document the cap and that anonymous/unbounded keying is the operator's responsibility.

- **Per-run EventLog is unbounded; "backpressure" is actually unbounded buffering** — §3 claims "backpressure" and "no event loss," but each run's `Vec&lt;AgentEvent&gt;` retains *every* event — including high-volume `TokenDelta`/`ReasoningDelta` (`agent.rs:329-351`) — for the full retention window, with no per-run cap. The writer never blocks on slow clients (good for not stalling the agent) but that is the opposite of backpressure. With 1024 retained runs (§4) × thousands of deltas each, memory is effectively unbounded. | Why it matters: streaming-heavy workloads can OOM the server; the §3 "backpressure" property is mischaracterized. | Suggested fix: cap events-per-run (or bytes), and reframe §3 as "decoupled buffering with bounded retention," documenting the memory cost.

- **Concurrent same-session requests race; in-scope but unaddressed** — `SessionProvider` returns the *same* `Arc&lt;dyn Session&gt;` per `X-Session-Id`. The runner does snapshot → run → append (`runtime-tokio/src/lib.rs:97-129, 207-217`), a read-modify-write. Two concurrent requests with the same id both snapshot empty, run blind to each other, and both append — corrupting conversation order. The session-affinity test (§8) is sequential only. | Why it matters: `X-Session-Id` is a first-class feature (§5/§11), so single-node concurrent same-session traffic (double-submit, multiple tabs) is in scope. | Suggested fix: serialize runs per session id (per-session async lock/queue), or explicitly document "no intra-session concurrency control; concurrent same-session requests race" and test that boundary.

- **`router(&amp;self)` spawning the sweeper is a hidden side effect with two hazards** — §4 says the sweeper is "spawned by `serve()` and by `router()`" and holds a `Weak`. `router(&amp;self)` (§5) is a sync method whose "mount into a larger app" use case is typically called while building the app. `tokio::spawn` panics outside a runtime; calling `router()` twice spawns two sweepers. Worse, the spec never states the **Router's handler state holds a strong `Arc&lt;RunRegistry&gt;`** — if it mirrors the sweeper's `Weak`, the registry dies when the `AgentServer` is dropped (the very pattern §4's "exits when the server is dropped" suggests) and every handler 404s. (Contrast `mcp`'s `streamable_http_service()`, which is pure — `mcp/src/server.rs:151-160`.) | Why it matters: panic-outside-runtime and a premature-drop/404 hazard on the primary integration entry point. | Suggested fix: make `router()` pure (no spawn); spawn the sweeper in `serve()` or lazily on first request; explicitly state the router state owns a strong `Arc&lt;RunRegistry&gt;` and the sweeper a `Weak`.

- **Cancel-on-disconnect conflicts with replay and async mode; under-specified** — §6 says client disconnect cancels the run's `CancellationToken`, yet §4 says runs are retained/replayable and §5's `?mode=async` *must* survive the creating client's disconnect. A run can also have multiple subscribers (plain awaiter + SSE + WS); cancelling on any one drop kills it for all. | Why it matters: naive "cancel on subscriber drop" will abort async runs and shared runs. | Suggested fix: scope cancellation to non-async, single-owner requests; specify the drop-guard mechanism and what happens to a run with zero remaining subscribers vs. an async run.

### MINOR

- **`http` is not a workspace dependency** — §9 lists `http` as "already in `[workspace.dependencies]`"; it is not (`Cargo.toml:16-78`). The trait signatures use `http::request::Parts` (§5). | Fix: use the `axum::http` re-export (no new dep), or add `http` to `[workspace.dependencies]` — but correct the false claim.

- **`RunResult`/`AgentInput` are not (de)serializable** — `RunResult` derives only `Debug, Default, Clone` (`runner.rs:208`); `AgentInput` only `Debug, Clone, Default` (`agent.rs:88`). So "200 aggregated `RunResult` JSON" can't be `Json(run_result)`, and the request body can't deserialize into `AgentInput`. The spec defers the body shape (§6) — fine — but the plan must budget hand-rolled DTOs (plus their own `///` docs). `AgentEvent`/`TokenUsage`/`Item` are serde-ready (`agent.rs:311`, `runner.rs:414`, `item.rs:18`).

- **The curl AC one-liner won't work as written** — `curl -d '{"input":"hello"}' .../runs` (§5, line 198) sends `Content-Type: application/x-www-form-urlencoded`; axum's `Json` extractor 415s without `application/json`. | Fix: document `-H 'Content-Type: application/json'` in the AC, or accept a lenient body extractor.

- **`serve(impl Into&lt;SocketAddr&gt;)` rejects string literals and hides the bound port** — Unlike `mcp`'s `&amp;str` + `TcpListener::bind` (`mcp/src/server.rs:165-172`), `impl Into&lt;SocketAddr&gt;` won't accept `"127.0.0.1:8080"`, and consuming `self` without returning the local addr blocks ephemeral-port (`:0`) discovery. Tests can still bind their own listener via `router()`, so it's not fatal. | Fix: take `impl ToSocketAddrs` (or `&amp;str`) and/or expose the bound addr.

- **Untagged request enum gives poor 400s, and "LRU" is really FIFO-by-completion** — (a) The `{messages}`/`{input}` discriminators are disjoint so untagged *works*, but untagged enums yield the unhelpful "did not match any variant" error and buffer the body, making clean 400s hard — prefer a custom `Deserialize`. (b) §4's "LRU" never updates recency on replay access, so it's oldest-completed-first eviction; an actively-replayed old run keeps streaming (the WS/SSE handler holds an `Arc&lt;RunHandle&gt;`) but becomes undiscoverable for new lookups. Clarify the wording.

- **WebSocket details thin** — §5's `{name}` in the WS path is redundant given the UUID run id; behavior on name/id mismatch is unspecified; and the handler must still poll the inbound half to observe client close (else disconnect/cancel won't fire). The "close before upgrade" mechanism (return non-101, e.g. 404, before `on_upgrade`) is achievable but should be stated.

- **`Notify` lost-wakeup needs the precise pattern** — §3's note is directionally right, but correctness requires pinning the `notified()` future and `enable()`-ing it *before* re-reading the log; merely constructing the future doesn't register the waiter. Pin the exact pattern in the plan.

- **Full doc surface vs `missing_docs`/doc-coverage gates** — The stub opts into `[lints] workspace = true` (`runtime-axum/Cargo.toml:15-16`), so every public item (builder's ~10 methods, three provider traits, two default providers, `ServerError`/`AuthRejection` and each variant) needs `///` under `-D warnings`, plus the 80% coverage gate. Not called out in §8; budget for it.

### QUESTIONS

- How does `AuthLayer` pass authenticated identity to `ContextProvider`? Both take `Parts`; the idiomatic answer is `parts.extensions` (AuthLayer takes `&amp;mut Parts`, ContextProvider `&amp;Parts`), but the spec doesn't say, and without it auth can't influence `Ctx`.
- Is the published crates.io `paigasus-helikon-core` (pin `0.5.12`, `Cargo.toml:96`) confirmed to already export everything used (`RunResultStreaming`, `MemorySession`, etc.)? The "no same-PR core bump" claim (§10) hinges on it — verify against the registry, not just the local tree.
- For a run created by plain POST whose client disconnects: the spec says cancel *and* retain for replay — is replaying a deliberately-aborted (`RunFailed { "run cancelled" }`) run the intended UX, or should disconnect-without-async simply evict?
- Every new dependency (`uuid`, `utoipa`) must clear `deny.toml`'s license/advisory allowlist on the `audit`/`deny` required checks — has utoipa's transitive graph been checked (it can pull proc-macro-heavy deps)?

## What's good
- The append-only `EventLog` + `Notify` design (§3) is genuinely well-reasoned: replay == live via a single code path, no broadcast-lag loss, and the rejected alternatives (raw `broadcast`, per-subscriber `mpsc`) are correctly dismissed. Preserve this.
- Executing through the core `Runner` trait rather than calling `agent.run()` directly (as `mcp` does, `mcp/src/server.rs:307`) is the right call — it gets session load/seed/persist and the durability seam for free, and the returned `RunResultStreaming.events` really is `BoxStream&lt;'static&gt;` (`runner.rs:248`), so the "spawn a writer task that owns and drains the stream" design *is* achievable (the user's flagged BLOCKER #2 does not hold — the only inaccuracy is calling the return type a bare `BoxStream` when it's `RunResultStreaming` whose `.events` is that stream).
- The release-engineering section (§10) is accurate against the repo: the `paigasus-helikon-runtime-axum` `release = false` block exists (`release-plz.toml:44-47`), the facade self-pin (`0.4.13`) and workspace pin pattern match, and the same-PR facade-bump rationale correctly reflects the SMA-346 cascade trap. Steps 1-5 are complete and correct; no core bump is needed.
