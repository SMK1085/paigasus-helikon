### Strengths

- **Batch-drain `subscribe` is correct and behaviorally sound.** I traced all three paths against the replaced per-event logic:
  - *No-eviction replay*: `next_cursor = first_seq + retained_len` = seq of the next-to-append event; the whole snapshot is drained from an owned `IntoIter`, then the next `read_from(cursor)` resumes exactly at the tail. No overlap, no gap.
  - *Under-range clamp*: `read_from` clamps `effective_cursor = cursor.max(first_seq)`, so an under-range `from` starts at the first retained event; verified against `subscribe_skips_gap_on_ring_eviction` (traced by hand: yields `[c, done]` exactly once each).
  - *Mid-replay eviction*: because the batch is cloned into `pending` before draining, concurrent eviction cannot drop or re-emit an in-flight batch. This is actually *stronger* than the old per-event code (which could skip a mid-batch event on a race) — strictly fewer drops, never a duplicate. Not a regression.
  - *Lost-wakeup ordering preserved*: `notified()`+`enable()` still precede every `read_from` that may return empty; the fast-path drain only runs when buffered data exists, so it never needs a wakeup. Correct.
- **Synthetic-frame invariant is airtight.** `start_error` is written in `spawn_writer` *before* the `TerminalGuard` drop calls `mark_terminal()` (runs.rs:306 then Drop) — so when a subscriber observes terminal and calls `synthetic_terminal_frame`, `start_error` is already visible (mutex + notify happens-before). A normally-completed run always retains its terminal event as the last element (nothing appends after it → never ring-evicted), so `saw_terminal` is always `true` and no spurious `RunFailed` is injected — proven live by `sse_stream_matches_local_events` and `ws_replays_completed_run_then_closes` staying green. The WS `socket.recv()` disconnect arm `break`s without calling `synthetic_terminal_frame`, so a client close emits no synthetic frame. One-shot (`oneshot_response`) is untouched — still `Err(ServerError::RunStart)` → 500.
